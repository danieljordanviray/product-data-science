Active, New, and Returning Users (Over Time)

November 3, 2026

Author: Daniel Jordan Viray

Product analytics · SQL + Power BI / DAX · one flag that splits every period’s users into new and returning

Who this is for: product data scientists building dashboards that executives and product managers will filter themselves. The calculation has to stay correct no matter what date range the viewer picks — that constraint, not the arithmetic, is the whole problem.

The setup. A platform launched on January 11, 2026, and members have been using it since. Today is November 3, 2026. Every session is one row: a member, a session, and when it happened. For any time period we want three numbers, related by one identity:

Active Users = New Users + Returning Users
Active — distinct members with at least one session in the period. New — active members whose first-ever session is in the period. Returning — active members whose first-ever session was before the period started.

Step 1 — add one column: is_first_session

Flag each session row: 1 if it is that member’s first-ever session on the platform, 0 otherwise. Exactly one row per member gets a 1. The decisive detail is when this is calculated: in the dataset, at refresh time, over the member’s entire history — before any dashboard filter exists. A filter applied later can hide rows, but it can never move a flag.

SQL

SELECT
    member_id,
    session_id,
    session_timestamp,
    CASE
        WHEN ROW_NUMBER() OVER (
                 PARTITION BY member_id
                 ORDER BY session_timestamp, session_id
             ) = 1
        THEN 1 ELSE 0
    END AS is_first_session
FROM sessions;

ROW_NUMBER() restarts the count at 1 for each member, ordered by time — so the 1 lands on the earliest session, with Session ID breaking any exact-timestamp tie. (To filter or aggregate on the flag, wrap this in a CTE or subquery, since window functions are computed after WHERE.)

Power BI (DAX calculated column)

is_first_session =
VAR FirstSessionAt =
    CALCULATE (
        MIN ( Sessions[Session Timestamp] ),
        ALLEXCEPT ( Sessions, Sessions[Member ID] )
    )
RETURN
    IF ( Sessions[Session Timestamp] = FirstSessionAt, 1, 0 )

ALLEXCEPT reads as “this member’s earliest session, ignoring everything else.” Because this is a calculated column, Power BI evaluates it once at refresh, over full history — slicers never touch it. (If a member could have two sessions at the exact same timestamp, both would flag 1; the distinct-member counts below are still right, but prefer the SQL ROW_NUMBER() version if you also need to count first sessions.)

Step 2 — the three measures

-- Power BI (DAX measures)
Active Users =
DISTINCTCOUNT ( Sessions[Member ID] )

New Users =
CALCULATE (
    DISTINCTCOUNT ( Sessions[Member ID] ),
    Sessions[is_first_session] = 1
)

Returning Users =
[Active Users] - [New Users]
-- SQL (same three numbers, for any window [@start, @end])
WITH flagged AS ( /* the Step 1 query */ )
SELECT
    COUNT(DISTINCT member_id) AS active_users,
    COUNT(DISTINCT CASE WHEN is_first_session = 1
                        THEN member_id END) AS new_users,
    COUNT(DISTINCT member_id)
      - COUNT(DISTINCT CASE WHEN is_first_session = 1
                            THEN member_id END) AS returning_users
FROM flagged
WHERE session_timestamp >= @start AND session_timestamp < @end;

Read New Users literally: distinct members who have, inside the period the viewer selected, a session carrying the flag. The date filter and the flag intersect — a flagged session only counts if it also falls in the selected window.

6 = 6 + 0. ✓

Watch out — returning users ≠ repeat sessions. Returning = 0 over the full period surprises people, because A clearly came back in February and July. Both things are true, about different units. Classified as a user in this period, A is new: she was acquired inside it, and a member gets exactly one classification per period. Counted as sessions, 6 of the 12 sessions are repeat sessions (flag 0). Keep the two sentences separate in reviews — “half our sessions are repeat visits” and “zero of this period’s users are returning users” describe the same table.

Now walk it member by member — what survives for each person decides how that person is counted in this window:

  • Member A — 1 of 3 sessions survives. S01 (her flagged first session, Jan 11) and S04 (Feb 10) drop off; S08 (Jul 14, flag 0) survives. The window can see A using the platform but cannot see her first session — so A counts as active and returning, not new.
  • Member B — 1 of 2 sessions survives. S02 (his flagged first session, Jan 11) drops off; S11 (Oct 5, flag 0) survives. Same story as A: active and returning, not new.
  • Member C — 0 of 2 sessions survive. Both S03 (Jan 20) and S05 (Mar 8) drop off. C has no session in the window at all, so C counts in nothing for this window — not active, not new, not returning. Filtering a member completely out of view removes them from every count, which is correct: this window is not about C.
  • Member D — 1 of 2 sessions survives. S06 (his flagged first session, Apr 15) drops off; S09 (Aug 22, flag 0) survives. Active and returning, not new.
  • Member E — 2 of 2 sessions survive. S07 (Jun 15) is after the filter start, and it carries the flag — her first-ever session is genuinely inside this window. E counts as active and new. (S10, Sep 18, also survives; it doesn’t change her classification.)
  • Member F — 1 of 1 session survives. S12 (Nov 3) is flagged and inside the window — F joined today. Active and new.

Add up the walk: 5 members have at least one surviving session (active), 2 of them have a surviving flagged session (new), and the other 3 active members’ flags sit in the red rows (returning). That is exactly the summary:

MeasureMembersCount
Active usersA, B, D, E, F — everyone who used the platform in the window, new or not5
New usersE, F — the only members whose flagged session falls in the window2
Returning usersA, B, D — active in the window, flagged back in Jan/Apr3

5 = 2 + 3. ✓ The calculation is robust to the filter for one reason: A’s, B’s and D’s flags were fixed in January and April, in the dataset. The filter can hide their first sessions from view — it cannot re-flag their July, October and August sessions as firsts.

Contrast with the broken version: if “first session” were recalculated after filtering (a MIN() inside a measure over visible rows), each active member’s first visible session would flag — new would read 5 and returning 0, every window, forever. A dashboard whose returning count is always zero is telling you the flag is being computed in the wrong place.

Watch out — the subtraction order is the whole formula. Returning = Active − New, never New − Active. The Jun 1 window makes the error self-revealing: 2 − 5 = −3, and a user count can’t be negative. If a returning number ever comes out negative, the subtraction is flipped (or the new count is inflated by a post-filter flag).

The two dashboard charts — the practical implementation

That is the whole job now. The dataset is the flagged sessions table (Member ID, Session ID, Session Timestamp, is_first_session), plus one helper column for the day on its own:

Session Day =
DATE (
    YEAR ( Sessions[Session Timestamp] ),
    MONTH ( Sessions[Session Timestamp] ),
    DAY ( Sessions[Session Timestamp] )
)

Put one date slicer on Session Day on the dashboard. Both charts below use Session Day as their axis (set the axis type to Continuous), so both respond to that one slicer. The examples show the slicer set to June 1, 2026 → November 3, 2026.

Chart 1 — per day: active users and new users

Use the two measures from Step 2, unchanged. No new calculation is needed — each measure is evaluated once per day on the axis, inside whatever range the slicer selected:

Active Users =
DISTINCTCOUNT ( Sessions[Member ID] )

New Users =
CALCULATE (
    DISTINCTCOUNT ( Sessions[Member ID] ),
    Sessions[is_first_session] = 1
)

How to read it, simply. For each day: the gray point is how many distinct members used the platform that day, and the blue point is how many of them were using it for the first time ever. Blue can never sit above gray. The gap between them on a day is that day’s returning users (Jul 14: gray 1, blue 0 — one person used the platform, and she was returning). Days with sessions are the only days with points; change the slicer and you simply see a different set of days — the value on any given day never changes, because the flag was fixed in the dataset.

Chart 2 — cumulative new users, within the selected period

Yes — this chart needs nothing fancier than the flag itself. Because exactly one row per member carries a 1, adding up the flag is counting new users: SUM(is_first_session) on a single day is that day’s new users, and over a whole period it is the period’s new users. So Chart 2 is just a running total of SUM(is_first_session): put Session Day on the axis, that sum on the values, and either apply a “Running total” quick measure to it, or write the running total as one measure:

New Users (from the flag) =
SUM ( Sessions[is_first_session] )

Cumulative New Users =
VAR CurrentDay = MAX ( Sessions[Session Day] )
RETURN
CALCULATE (
    SUM ( Sessions[is_first_session] ),
    FILTER (
        ALLSELECTED ( Sessions[Session Day] ),
        Sessions[Session Day] <= CurrentDay
    )
)

Reading it: ALLSELECTED keeps only the days inside the range the viewer selected, which is what makes the line restart at the beginning of each new selection; <= CurrentDay adds the flag up from the start of that range through the day being plotted. Same line, either way — quick measure or DAX.

How to read it, simply. The line starts at 0 on the first day of the selected period. It steps up only on days when somebody joined, by however many joined that day (Jun 15: up 1, for E). It stays flat on days when only returning users showed up, however busy those days were. And the height of the line at the end of the period is the headline number: the total new users captured in the selected period — here, 2. Move the slicer to the full range (Jan 11 → Nov 3) and the same chart ends at 6, because all six members joined inside that range.
